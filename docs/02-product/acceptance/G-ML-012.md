# Acceptance Contract: G-ML-012

**Goal:** G-ML-012: Model Packaging, Checkpoint Versioning and Provenance Ledger  
**Epic:** ML  
**Version:** 1.0.0  
**Status:** active  

---

## 1. Feature Definition

```gherkin
Feature: Model Packaging, Checkpoint Versioning and Provenance Ledger
  As an Autonomous Agent Kernel and Production Deployment Pipeline
  I want to package trained LoRA adapter weights, value head parameters, and calibration configs into a cryptographically sealed release bundle
  So that every deployed artifact is immutable, verifiable via SHA256 checksums, and bound to exact-HEAD git provenance.
```

---

## 2. BDD Given-When-Then Scenarios

### Scenario 1: Cryptographic Manifest and Checksum Generation
```gherkin
Scenario: Sealed Release Manifest with SHA256 Verification
  Given trained LoRA adapter weights, value head weights, tokenizer, and calibration configs
  When the packaging script executes package consolidation
  Then a sealed directory `models/checkpoints/v1.0.0/` MUST be produced
  And `models/checkpoints/v1.0.0/manifest.json` MUST be created containing valid RFC 8259 JSON
  And every artifact listed MUST have a calculated SHA256 hex digest matching its physical byte content.
```

### Scenario 2: Exact-HEAD Git Provenance Binding
```gherkin
Scenario: Provenance Traceability to Exact Git Commit
  Given a repository at a clean or tracked git state
  When the model packaging script compiles the release bundle
  Then `manifest.json` MUST record the exact 40-character git commit SHA (`git rev-parse HEAD`)
  And `manifest.json` MUST record base model digest, adapter SHA256, and training recipe hash
  And any discrepancy in commit hash or missing provenance MUST fail packaging with non-zero exit code.
```

### Scenario 3: Safetensors Serialization and Reload Verification
```gherkin
Scenario: Safetensors Weight Serialization and Tamper-Proof Reload
  Given the packaged release bundle containing safetensors weights
  When `python code/ml/scripts/package_model.py --verify-checksums` is executed
  Then all `.safetensors` files MUST be reloaded into memory using safetensors deserialization
  And the recomputed SHA256 checksums MUST match manifest entries with 100% identity
  And the verification command MUST exit with status code 0.
```

### Scenario 4: Fail-Closed Corruption and Tamper Rejection
```gherkin
Scenario: Immediate Abort on Weight Modification or Corrupted Manifest
  Given a packaged release bundle where any byte in a safetensors file or config has been modified
  When the package verification command `--verify-checksums` executes
  Then the verification MUST fail immediately
  And a descriptive error detailing the corrupted file and digest mismatch MUST be logged
  And the process MUST terminate with a non-zero exit code.
```

### Scenario 5: Model Card Documentation with Training Provenance
```gherkin
Scenario: Comprehensive Model Card Documentation
  Given the packaged checkpoint release
  When model card documentation is generated in `docs/06_raw/model_card_v1.0.0.md`
  Then the document MUST detail training hyperparameters, loss formulations (RLCD, asymmetric penalty), evaluation benchmarks, and safety thresholds
  And the model card MUST cross-reference the exact git commit and manifest digest.
```
