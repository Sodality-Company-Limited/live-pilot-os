# Acceptance Contract: G-ML-022

**Goal:** G-ML-022: Upgrade Engine and Downstream-Project Distribution  
**Epic:** ML  
**Version:** 1.0.0  
**Status:** active  

---

## 1. Feature Definition

```gherkin
Feature: Upgrade Engine and Downstream-Project Distribution
  As a Soda OS Framework Maintainer and Downstream Project Integrator
  I want the `soda-os upgrade` CLI engine to synchronize confidence calibration assets, contracts, and harnesses non-destructively
  So that existing downstream repositories gain calibrated uncertainty guarantees, quality gates, and dynamic routing capabilities without losing custom project configurations or business logic.
```

---

## 2. BDD Given-When-Then Scenarios

### Scenario 1: Manifest Asset Registration & YAML Conformance
```gherkin
Scenario: Framework Manifest Parses Cleanly and Declares Calibration Modules
  Given the framework manifest file `template/framework-manifest.yml`
  When parsed as YAML
  Then it MUST contain `calibration` entries under `overwrite`
  And it MUST declare `scripts/lib/confidence-calibration.mjs`
  And it MUST declare `scripts/harness/confidence-calibration-harness.mjs`
  And it MUST declare destination paths and merge strategies without syntax errors.
```

### Scenario 2: Non-Destructive Configuration Merger Preserving Custom Keys
```gherkin
Scenario: Deep Merging Default Calibration Thresholds into Existing Custom Configurations
  Given a target project configuration containing custom application keys and user-tuned parameters
  When `mergeCalibrationConfig(existingConfig, defaultThresholds)` is executed
  Then all existing custom application keys MUST remain unmodified
  And user-tuned parameters MUST NOT be overridden by default values
  And missing default calibration thresholds (`max_ece`, `max_brier`, `max_hcer`, `tau_low`, `tau_high`) MUST be populated.
```

### Scenario 3: Downstream Project Upgrade Distributing Calibration Modules
```gherkin
Scenario: Upgrading Downstream Project Copies Calibration Libraries and Harnesses
  Given a downstream application project missing calibration libraries
  When `soda-os upgrade <path> --yes` is executed
  Then `scripts/lib/confidence-calibration.mjs` MUST be created in the target project
  And `scripts/harness/confidence-calibration-harness.mjs` MUST be created in the target project
  And target project custom code in `code/**` MUST remain untouched
  And the upgrade engine MUST report successful file synchronization.
```

### Scenario 4: Dry-Run Mode Invariant (Zero Target Mutations)
```gherkin
Scenario: Upgrade Dry-Run Mode Executes without Modifying Filesystem
  Given a target project directory
  When `soda-os upgrade <path> --dry-run` is invoked
  Then the process MUST exit with code 0
  And stdout MUST report prospective changes
  And NO files on disk in the target project directory may be modified or created.
```

### Scenario 5: Full Upgrade Test Suite Execution (Exit 0)
```gherkin
Scenario: Comprehensive Upgrade Integration Test Battery
  Given the test suite `tests/unit/test-upgrade-calibration.mjs`
  When executed via `node tests/unit/test-upgrade-calibration.mjs`
  Then all unit and integration test assertions MUST pass 100% green
  And the process MUST exit cleanly with code 0.
```

---

## 3. Measurable Acceptance Criteria Checkpoints

- [ ] `template/framework-manifest.yml` declares calibration assets under `overwrite.calibration`.
- [ ] `cli.js` exports and implements `mergeCalibrationConfig()` non-destructively.
- [ ] `soda-os upgrade` successfully distributes calibration libraries and harnesses to downstream project directories.
- [ ] Preserves existing custom project configurations while adding default calibration thresholds.
- [ ] `tests/unit/test-upgrade-calibration.mjs` executes cleanly with exit code 0.
