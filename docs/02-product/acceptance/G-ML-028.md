# Acceptance Contract: G-ML-028

**Goal:** G-ML-028: DAVE Model Evaluation, Promotion, Drift, and Rollback  
**Epic:** ML  
**Version:** 1.0.0  
**Status:** active  

---

## 1. Feature Definition

```gherkin
Feature: DAVE Model Evaluation, Promotion, Drift, and Rollback
  As a System Architect and Production Platform Operator
  I want an automated model promotion governor evaluating calibration drift, overconfidence regression, cryptographic checkpoint provenance, and zero-downtime atomic rollbacks
  So that Soda OS guarantees that no candidate checkpoint can be promoted if it degrades calibration or safety, while automatically executing sub-second rollbacks upon runtime telemetry drift.
```

---

## 2. BDD Given-When-Then Scenarios

### Scenario 1: Multi-Criteria Model Promotion Evaluation
```gherkin
Scenario: Candidate model checkpoint is evaluated against the 6 promotion invariants
  Given a candidate model checkpoint with evaluation metrics and a stable baseline model
  When `DaveModelGovernor.evaluatePromotion` evaluates the promotion policy
  Then the governor MUST approve promotion if and only if all 6 invariants pass:
    | Invariant | Condition |
    | ECE Drift | ECE_new <= ECE_baseline + 0.010 |
    | Accuracy | Acc_new >= Acc_baseline - 0.010 |
    | Overconfidence Rate | Overconfidence_Rate <= 0.020 |
    | Unsafe Autonomy Rate | Unsafe_Autonomy_Rate == 0.000 |
    | Brier Score Drift | Brier_new <= Brier_baseline + 0.020 |
    | HCER Drift | HCER_new <= HCER_baseline |
  And the evaluation MUST fail-closed with detailed diagnostic reasons if any invariant is breached.
```

### Scenario 2: Overconfidence Regression and Calibration Drift Rejection
```gherkin
Scenario: Candidate with degraded ECE or overconfidence is rejected fail-closed
  Given a candidate checkpoint exhibiting higher task accuracy but worsened ECE or overconfidence rate > 0.020
  When `DaveModelGovernor.evaluatePromotion` assesses the candidate
  Then promotion MUST be rejected with `approved: false`
  And the candidate model MUST NOT be promoted to active production.
```

### Scenario 3: Cryptographic Checkpoint Provenance and Signature Verification
```gherkin
Scenario: Checkpoint provenance manifest and HMAC-SHA256 signature verification
  Given a model provenance manifest specifying dataset lineage SHA-256, tokenizer hash, config hash, and artifact tensor hashes
  When `verifyModelProvenance` validates the manifest and its cryptographic signature
  Then all digests MUST match declared physical files or lineage hashes exactly
  And tampered signatures or altered artifact bytes MUST cause fail-closed rejection with descriptive error diagnostics.
```

### Scenario 4: Promotion Receipt Recording into Immutable Proof Ledger
```gherkin
Scenario: Approved promotion records immutable receipt into proofs ledger
  Given an approved candidate model meeting all 6 invariants and verified provenance
  When `createPromotionReceipt` and `recordPromotionReceipt` serialize the receipt
  Then the receipt MUST be saved to `artifacts/proofs/G-ML-028-promotion-receipt.json`
  And it MUST contain `schema_version: 1`, `certification: 'PASS'`, `promotion_status: 'APPROVED'`, all 6 invariant results, and HMAC-SHA256 signature.
```

### Scenario 5: Zero-Downtime Atomic Rollback on Runtime Drift Detection
```gherkin
Scenario: Real-time telemetry drift triggers automatic rollback to baseline within 100ms
  Given an active candidate model serving production traffic
  When `ModelRollbackStateMachine.monitorStreamingTelemetry` detects runtime calibration drift (ECE > 0.08 or HCER > 0.05)
  Then `triggerRollback` MUST atomically swap the active production pointer back to the previous stable baseline
  And total rollback execution latency MUST be strictly under 100ms (typically < 2ms)
  And state MUST transition cleanly to `ROLLED_BACK` with full telemetry event audit.
```
