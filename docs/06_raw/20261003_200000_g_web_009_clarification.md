## 1. Context & Business Intent

In high-performance enterprise user interfaces and mission-critical agentic operating systems, UI motion is not decorative ornamentation; it is a vital cognitive feedback mechanism that establishes spatial orientation, visual hierarchy, and state continuity. However, undisciplined animation architectures introduce two catastrophic failure modes:
1. **Performance Degradation (Jank / Frame Drops):** Animating CSS layout properties (`width`, `height`, `top`, `left`, `margin`, `padding`) forces the browser rendering engine to trigger CPU-bound layout reflows and repaints on every frame, violating the 16.6ms frame budget (60fps).
2. **Accessibility & Cognitive Barriers:** Arbitrary, protracted durations (>300ms) degrade perceived performance and operational latency, while lack of respect for user vestibular preferences causes nausea, vertigo, and cognitive fatigue in users with vestibular disorders.

Goal `G-WEB-009` codifies and programmatically enforces a strict, mathematical motion choreography system for Soda OS that guarantees:
- **60fps GPU-Accelerated Compositing:** All animated transitions and keyframes strictly utilize GPU-accelerated compositing properties (`transform` and `opacity`).
- **Bounded Duration Ceiling:** Micro-interactions and state transitions are strictly capped at a maximum of 300ms (`--motion-duration-max: 300ms`), with fast interactive feedback at 150ms and standard transitions at 200ms.
- **Natural Velocity Curves:** Prohibits unnatural linear easing, enforcing cubic-bezier curves (`--motion-ease-standard`, `--motion-ease-decelerate`, `--motion-ease-accelerate`, `--motion-ease-spring`).
- **Reduced Motion Invariant:** Complete collapse of duration and transition intervals for users who declare `prefers-reduced-motion: reduce` in compliance with WCAG 2.2 Success Criterion 2.3.3.

### `[UNDETERMINED_DYNAMICS]` (Resolved via Architectural Invariants)
1. **Linear Easing Prohibition:** UI transitions must avoid `linear` easing for interactive state changes, as linear motion feels mechanical and unnatural; cubic-bezier deceleration curves must be applied for entering elements and acceleration for exiting elements.
2. **Layout Thrashing Static Audit:** An automated harness must scan all CSS and TSX source files to mathematically prove that no `@keyframes` rules animate layout or paint properties (`top`, `bottom`, `left`, `right`, `width`, `height`, `margin`, `padding`).
3. **Reduced Motion Collapse Mechanism:** `prefers-reduced-motion` must collapse animation durations to `0.01ms !important` rather than `0s !important` to ensure that transition completion JavaScript events (`transitionend`, `animationend`) still fire reliably in browser event loops.

## 4. Multi-Choice Architectural Decision Ledger

### Question 1: How should 60fps frame rate budgets be enforced without heavy runtime browser instrumentation?
- **Option A:** Launch headless Chromium with Chrome DevTools Protocol (CDP) tracing to capture frame rendering timestamps on every CI run (heavyweight, volatile, dependent on host GPU virtualization).
- **Option B (Recommended):** Static layout-thrashing property analysis combined with CSS hardware-acceleration invariants. Scan all `@keyframes` and transitions across all stylesheets and components to mathematically guarantee that only compositor-only properties (`transform`, `opacity`) are animated. *(Zero external dependencies, sub-millisecond execution, mathematically foolproof)*.

### Question 2: How should `prefers-reduced-motion` overrides be structured?
- **Option A:** Apply `animation: none !important; transition: none !important;` globally. *(Problematic: Breaks JavaScript state machines relying on `transitionend` and `animationend` callbacks)*.
- **Option B (Recommended):** Set `animation-duration: 0.01ms !important; transition-duration: 0.01ms !important; animation-iteration-count: 1 !important;` under `@media (prefers-reduced-motion: reduce)`. *(Ensures instant visual transitions for vestibular safety while cleanly triggering lifecycle completion events)*.

### Question 3: What is the maximum acceptable duration for user interaction transitions?
- **Option A:** 500ms (common default in legacy desktop applications; feels sluggish in modern agentic interfaces).
- **Option B (Recommended):** 300ms ceiling (`--motion-duration-max: 300ms`), with standard micro-interactions set to 150ms–200ms. *(Meets human cognitive perception thresholds for instantaneous responsiveness)*.
